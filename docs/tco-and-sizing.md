# 容量、成本与部署决策

## 先收集输入

售前不应该从“选哪个模型”开始，而应该收集：

- 峰值并发、平均并发、日请求量和峰值持续时间。
- 输入/输出 token、上下文长度、检索片段数量和多轮比例。
- TTFT、完整答案 p50/p95、错误率和可接受排队时间。
- 数据驻留、网络隔离、审计、权限和高可用要求。
- 现有 CPU/GPU、显存、磁盘、运维团队和升级窗口。
- 云 API 单价、限流、最低承诺、私有化硬件和人力成本。

仓库中的 `estimate_capacity` 只把并发输入映射为“需要哪类压测”，不会编造 tokens/s、SLA 或采购数量。

## 决策矩阵

| 路径 | 适合 | 需要证明 | 典型下一步 |
|---|---|---|---|
| 云端 API | 快速建立质量基线、流量弹性 | 数据出域、供应商 SLA、单请求成本 | 用黄金集跑质量与价格基线 |
| llama.cpp + GGUF | 低并发、边缘、本地数据 | 目标硬件质量/容量、量化损失、升级方式 | 在目标设备测 TTFT/p95/RSS |
| vLLM + GPU | 共享 GPU、较高并发、多适配器 | 显存、批处理、隔离、可用性、运维 | 在目标 GPU 做峰值压测 |
| 混合 | 质量/合规边界尚未确定 | 路由、数据分类、两套运维 | 云端建基线、本地做边界验证 |

## 成本模型

不填入未经实测的数字，只保留变量：

```text
云端月成本 = 输入 tokens × 输入单价
           + 输出 tokens × 输出单价
           + 检索/存储/网络/可观测性成本

本地月成本 = GPU/CPU 折旧或租赁
           + 电力与机房
           + 模型/知识库运维人力
           + 备份、监控、高可用与升级成本
```

最终报价输入应由实际供应商价格、客户硬件报价、真实流量和压测结果填充。任何演示数字都必须标注日期、地域、税费、模型版本和假设。

## POC 到生产的门槛

只有当业务质量、权限/安全、性能、故障恢复和成本假设都被验证，才从“技术可行”进入“生产建议”。单个量化文件更小或一次 demo 更快，不能单独证明总体 TCO 更优。
