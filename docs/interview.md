# Interview Notes

## 1. 为什么选择这两个项目

“我刻意选择了两个不同层次的项目。Dify 证明我能把客户需求和企业资料组织成可交付的 AI 应用；llama.cpp 证明我理解模型服务背后的硬件、量化、延迟和成本。一个偏解决方案落地，一个偏基础设施选型。”

## 2. 为什么不只调用一个 API

“API 适合快速验证和高质量模型能力，但客户可能有数据不能出域、网络不稳定或模型版本固定的要求。因此我额外做了本地推理路径，并用实测数据比较质量、延迟、吞吐和运维成本。”

## 3. RAG、微调和提示词如何选择

“知识经常更新、需要引用来源时优先 RAG；需要改变模型稳定行为或输出风格时考虑微调；需求主要是格式、角色和流程约束时先用提示词。售前项目里我先用 RAG，因为资料更新和可追溯比记住固定知识更重要。”

## 4. 如何降低幻觉

“先限制上下文来源，再强制返回证据；没有召回结果时拒答或追问。价格、SLA、认证、合规和容量属于高风险结论，不能由模型自行承诺，要进入人工确认。”

## 5. 量化的取舍是什么

“量化可以降低模型文件和内存占用，也可能提高推理速度，但会有质量损失。不能只看 Q4 或 Q8 的文件大小，我会在目标业务问题、目标硬件和目标并发下测首 Token、生成速度、p95 和结构化输出通过率。”

## 6. Dify 和 llama.cpp 如何组合

“Dify 位于应用层，负责知识库、工作流和 API；llama.cpp 位于模型服务层，提供本地 OpenAI-compatible 推理接口。上层通过统一接口切换远程 API 或本地服务，因此可以先做云端 PoC，再验证私有化方案。”

## 7. 如何从 PoC 走向生产

“先固定需求和黄金问题集，再测试知识覆盖、模型质量、权限、日志、延迟、并发和失败恢复。PoC 机器的结果不能直接当生产容量，需要在客户目标硬件、真实数据规模和峰值流量下重新压测。”

## 8. 哪些是你的工作

“上游提供平台和推理能力，我没有把它们的源码功能写成自己的成果。我的工作包括售前需求模型、合成知识资料、工作流约束、API 适配器、离线基线、评测脚本、部署脚本、风险规则和演示材料。”

## 9. API 失败怎么处理

“设置超时、错误信息和可重试边界；模型不可用时不输出伪造结果。离线测试使用 mock 模式，生产则记录模型版本、错误率和请求链路，必要时切换到备用模型或进入人工处理。”

## 10. 你会如何向客户解释选型

“先问数据是否允许出域、模型质量要求、峰值并发、时延目标、已有硬件和运维团队，再给出 API、本地或混合方案。选型结论必须带假设和验证计划，不能只给一个模型名称。”
